# Practical model qualification

Start with a few useful tasks, one slot, native verification and explicit fallback. A mandatory synthetic campaign is unnecessary. Model approval is permission for a provisional operating scope, not proof of quality or savings.

1. Verify the exact local artifact, runtime identity, loaded settings and available context. Preserve runtime guardrails and native authentication. No automatic load or lifecycle operation is implied.
2. Explain the proposed capabilities, limitations and operating budget. Obtain any missing owner approval for that exact model/settings/scope and routing activation. Reuse existing authorization. A normal starting input budget is 65,536 UTF-8 bytes of serialized supplied context; choose a smaller budget when runtime context or the task requires it. This is an operational limit, not a measured model ceiling. Changing it requires explicit owner authorization.
3. Select a small bounded set of actual project tasks: a cited multi-file summary, a test addition, and a small code change only when a real requirement exists. Supply relevant instructions, related files, acceptance criteria and protected paths. Avoid manufactured bugs, irrelevant padding and automatic trial repetition. Test-writing permission must be explicit even when code changes were approved earlier.
4. Submit each task once using durable task keys. Use a fresh lightweight pressure reading after identity checks and before POST. Normal and warning pressure permit admission; critical, unknown or stale readings defer new work. Do not interrupt healthy work or clear uncertain slots. The runtime owns loading fit; free-memory arithmetic and swap deltas are optional diagnostics. One slot needs no empirical concurrency campaign.
5. Native verification checks each candidate's meaning and executes the declared isolated checks. Apply accepted changes only through native tools after rechecking source hashes, then run destination checks. A syntactically valid answer is insufficient. Preserve stalled or ambiguous attempts; use the durable native fallback contract when work cannot proceed locally.
6. Record acceptance, native rewriting, fallback, delivery and later corrections in the project ledger. Keep synthetic results separate. Record actual reported input/output tokens when available; byte budgets and approximate token ranges must never masquerade as usage. Native token savings need attributable native overhead and a comparable baseline; missing data stays unknown. Additional comparison calls require separate consent.

For initial examples, aim for relevant contexts around 4,000–16,000 tokens when practical, not a mandatory minimum or demonstrated ceiling. The HTTP adapter currently lacks a qualified tokenizer. It screens UTF-8 byte length of the full prompt plus reserved output and 2,048 tokens of template allowance against discovered context. This conservative screen can reject text that would fit with exact tokenization; runtime context errors still trigger failure handling. The allowance is not tokenizer attestation. Output capacity includes the configured generation allowance; do not silently alter thinking settings.

Report observations by task type and context size, with the number of attempts and failures. A few accepted tasks justify continued supervised use in that scope; they do not establish general reliability. Broaden difficulty gradually through authorized normal work. Do not convert observed maxima into approval ceilings, infer maximum concurrency from weight size, or require proven savings before collecting evidence.

The optional synthetic pack and historical capacity measurements remain available. Their strict measurement conditions describe those experiments, not everyday admission. Shared slots cover participating helper clients only. [Approved model loading](model-loading.md) has separate consent and verification; it does not qualify inference quality. Higher concurrency, arbitrary-language quality and automatic native usage attribution require separate qualification.

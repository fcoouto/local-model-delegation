# Assess my Model

Assess an already downloaded and loaded text model without onboarding it. Save a private unapproved profile and evidence. Preserve existing approvals, native settings, visibility and routing.

Read [Assessment operations](references/operations.md) before execution. Reuse the named [Setup operations](../setup/references/operations.md) sections for prerequisites, state, connection and profile preparation; do not duplicate those procedures. Missing prerequisites mean one concrete next step, not automatic Setup, installation, downloading or loading.

1. **Select the project and useful work.** Require the owner's selected project and permission to inspect it. Accept a Git repository or an umbrella; use `assessment projects` to discover candidates and validate one or more explicit repository selections. Reuse selections already given. An umbrella is only a selection container: create separate packs and campaigns for each chosen repository. Ask which usual work matters if history cannot establish it. Follow [project campaigns](references/operations.md#project-campaigns-default) to inspect merged work and current sources, prepare 6–10 grounded assignments per selected specialty, and show the portfolio. Default eight per specialty per repository: two light, three medium, two high, one extra high. Show combined assignment and maximum submission totals before generation. Every constructed scenario must trace to actual project sources. Do not silently substitute generic fixtures or reduce requested coverage. `assessment choices` and **All supported abilities** belong to explicitly requested legacy fixture runs only.
2. **Prepare and preview.** Identify the exact model and settings, selected project and coverage, source provenance, measured runtime-supported output allowance/deadlines, maximum cycles/submissions, one-slot execution and native checks. Keep references and hidden checks private; review real-framework references before calling a pack runnable. Explain that this saves evidence without approval or routing changes. Do not promise an elapsed time.
3. **Obtain consent for this run.** Record the actual owner authorization for each frozen repository preview. One owner response may cover several previews only when all are explicitly listed; save consent separately for each campaign. Standing assessment permission is insufficient. Reuse consent already explicit in this conversation only when it covers every preview dimension; ask only for what is missing. Never infer consent from a deadline, earlier runs or a passing result. Declining means no generation and no repeated consent request.
4. **Execute or resume the same run.** Coordinate one trial at a time through the existing queue and native verification. Reconcile saved work before continuing. Never repeat a completed, failed or possibly submitted trial. A pause requires explicit resume; stop is terminal. Submitted work remains observable and verifiable. Safety or uncertainty blocks further progress; do not use native fallback to solve a trial.
5. **Report and stop.** For multiple repositories, present one overview with separate repository results and evidence links; never infer an umbrella-wide approval or cross-repository integration capability. Show passed/evaluated alongside planned and unfinished counts by specialty/difficulty/context, first-cycle and final success, failure reasons, evidence limits and independent approval/routing state. Slow correct work passes; interruptions remain inconclusive. Show provisional recurring-task coverage only with owner-confirmed frequencies for the tested mix. A single extra-high pass remains exploratory. New approval applies only to this project; generic or other-project evidence cannot establish project qualification. A report request is offline by default. Do not start onboarding after success, explanation or export requests.

Only an explicit request such as **“onboard this model”** hands the selected profile/run and evidence limits to **local-model-delegation:setup**. Read Setup's skill before continuing the handoff. It reuses valid evidence and asks one missing decision at a time: operating scope first, then routing activation. Do not ask the owner to onboard merely because an assessment finished.
